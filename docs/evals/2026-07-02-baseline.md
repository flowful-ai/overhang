## google/gemini-3-flash-preview — 2/2 before cost-cap abort

| case | pass | rendered | watertight | bbox | warnings | steps | tokens in/out | cost | time |
|---|---|---|---|---|---|---|---|---|---|
| pi5-enclosure | ✅ | ✅ | ✅ | ✅ | 1 | 2 | 975,532/1,093 | $0.4910 | 20.4s |
| l-bracket | ✅ | ✅ | ✅ | ✅ | 1 | 5 | 28,047/2,244 | $0.0208 | 25.0s |

The run aborted after two cases: the $0.50 cost cap tripped. Cause: the
pi5-enclosure case rendered successfully on step 1, and the SDK then echoed the
full tool result — including the base64 STL — back into the model context on
step 2: **~975k input tokens ($0.49) for one follow-up step.**

This is a production bug, not an eval artifact: the client strips `stlBase64`
from history *between* turns (`strip-stl.ts`), but nothing strips it from the
steps *within* a turn, so every self-correction step after a successful render
pays the full STL in tokens. Fix: `toModelOutput` on the shared tool so the
model never sees the STL (the UI still receives it).

## Failure modes discovered (answering "I don't know")

1. **Tool-call emission failure** (gemini-2.5-flash, 8/8 cases): the model
   never produces a valid tool call. Invisible in the UI beyond a generic
   failure.
2. **STL-in-context cost/noise bug** (all models, any multi-step turn after a
   successful render): ~1M junk tokens per follow-up step.
3. **Assembly export failure** (found while validating a prompt example): the
   system prompt tells the model to use `cq.Assembly()` for multi-part models,
   but the worker's `cq.exporters.export()` cannot export Assembly →
   `AttributeError: 'Assembly' object has no attribute 'exportStl'`. Multi-part
   designs (e.g. snap-fit box + lid) fail even when the model does everything
   right.
4. **Syntax errors carry no line number** (found by pytest while covering the
   error-detail changes): `ast.parse(code)` is called without
   `filename="<string>"`, so SyntaxError line reporting never fires.
